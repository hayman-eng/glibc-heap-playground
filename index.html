What this models (and what it simplifies)

A faithful teaching model of the ptmalloc free-chunk fast paths in glibc ~2.31–2.39 on x86-64. The point is to make the invisible linked lists visible while you drive malloc and free by hand.

Allocation path (malloc)

request2size rounds up: chunk = max(0x20, (req + 8 + 15) & ~15). The usable bytes reuse the next chunk's prev_size, so a 0x20 chunk serves 24 bytes. A request is satisfied in order: exact-size tcache bin → exact-size fastbin → first fit in the unsorted bin (split, remainder returns to unsorted) → carve from the top chunk.

Free path

A freed chunk lands in tcache if its size is ≤ 0x410 and the bin isn't full. Otherwise, if size ≤ 0x80 it goes to a fastbin; else to the unsorted bin. tcache and fastbin are singly linked (LIFO via fd); unsorted is doubly linked.

Hardening you can defeat

  • tcache double-free (since 2.29): each tcache entry carries a key. On free, a matching key triggers a scan of the bin; a hit aborts with free(): double free detected in tcache 2. Clear the key with edit to slip past it.
  • fastbin double-free: a single check compares the incoming chunk against the bin head (double free or corruption (fasttop)). Free a second chunk in between and the dup goes through.
  • safe-linking (since 2.32): the stored fd is mangled, (pos » 12) ^ ptr. The playground shows both the value you want returned and the mangled bytes you'd actually have to write at pos.

Deliberately left out

Chunk consolidation (forward/backward), small/large-bin sorting and binning, last-remainder nuances, per-thread arenas, and the top-chunk size integrity checks. They don't change the tcache/fastbin lessons and add noise. Treat returned sizes and the key as representative, not byte-exact to any one release.
